## HIGH — SSRF blocklist bypass via wildcard-DNS rebinding (fixed)

**Where:** `workers/shared/http.ts` → `validatePublicUrl()`
**Found by:** S6. Black-box probe of `/api/audit` (unreleased at the time).

`validatePublicUrl()` screened the *hostname string* for private/loopback
literals, but Workers has no DNS resolution API, so a public hostname that
resolves to a loopback address passed every check.

Confirmed exploitable, not theoretical:

```
BLOCKED  422  control: literal 127.0.0.1        rejected_target:blocked_port
*** ALLOWED ***  200  http://localtest.me/     fetched status=200 bytes=10703
```

`localtest.me` resolved to `127.0.0.1` and the worker fetched it. Same for
`127.0.0.1.nip.io`, `sslip.io`, `xip.io`, `lvh.me`.

**Why severity is bounded, not critical** — three things, all verified:

1. Cloudflare's edge refuses egress to link-local/metadata space regardless of
   hostname. `169.254.169.254.nip.io` failed with a *network* error, not a
   validation error — the edge stopped it, not the code.
2. The audit response never returns the fetched body. Only derived scalars
   (title, contact, tech, timings) come back, so a successful rebind yields a
   fingerprint, not a dump.
3. `rateLimitOr429` caps a caller at 10 probes/hour/IP.

**Fix:** deny-listed the wildcard-DNS services plus any hostname with an IP
embedded in a label (`10.0.0.1.nip.io`), and rewrote the header comment to state
plainly that this is a mitigation and not a security boundary. Re-verified: all
seven rebind vectors now `422 blocked_host`, and `https://example.com/` still
audits normally.

## MEDIUM — Admin console was frameable, with no CSP (fixed)

**Where:** `workers/admin-console/src/index.ts`

`_headers` is a Cloudflare **Pages** feature — it does not apply to Workers. So
the one page on the estate that renders an operator's admin UI shipped with:

```
content-security-policy          *** ABSENT ***
x-frame-options                  *** ABSENT ***
strict-transport-security        *** ABSENT ***
x-content-type-options           *** ABSENT ***
referrer-policy                  *** ABSENT ***
```

Confirmed frameable (`Sec-Fetch-Dest: iframe` → `200`, no `X-Frame-Options`, no
`frame-ancestors`). The console renders a token prompt, so this is a
clickjacking target: an attacker talks the operator into re-entering their admin
token into an overlaid form.

**Fix:** added a strict CSP to the console shell with `frame-ancestors 'none'`,
`form-action 'none'`, `object-src 'none'`, `base-uri 'none'`, plus XFO/nosniff/
HSTS/Referrer-Policy/COOP/CORP/Permissions-Policy.

The CSP must keep `'unsafe-inline'` for script and style — verified the console
is one self-contained page (1 inline `<script>`, 1 inline `style=`, 0 external
origins, 4 `onclick`, 0 `<form>` elements), so those allowances cost nothing and
the framing protections are unaffected. Verified post-fix: headers present,
inline script intact, `/admin/api/ledger` still 503 unauthenticated.

## MEDIUM — Gateway JSON responses had no security headers (fixed)

Every gateway response shipped `Cache-Control` and CORS, nothing else — no
nosniff, no XFO, no Referrer-Policy, no HSTS. Lower risk than the admin case
(JSON isn't framed meaningfully) but it's the same root cause: `_headers` doesn't
reach Workers, and only the Pages side had been hardened.

**Fix:** added the baseline to `jsonResponse()` in `workers/shared/cors.ts` so
all 16 services inherit it rather than each remembering.

## LOW / INFORMATIONAL

1. **TLS 1.0 and 1.1 accepted at the edge.** `openssl s_client` completed a
   handshake on both for `pwn4g3.pages.dev`. Fixable in the Cloudflare zone
   SSL/TL encryption mode; not a code issue. *Not fixed — dashboard change.*
2. **`security.txt` only at `/.well-known/`.** Root `/security.txt` → 404. The
   canonical location is correct, so this is cosmetic, but researchers do check
   root first.
3. **The gateway root publishes a complete endpoint map**, including which routes
   are admin-gated. For a security portfolio that's arguably the feature, but it
   is a free recon gift for anyone who asks. Left as-is deliberately.
4. **`/hive/status` returns 771 bytes of zero-width characters.** Initially
   flagged as possible stego exfil; on inspection it's layer 1 of the intended
   6-step hivemind chain, and the response headers say so. Decoded plaintext:
   `{"service":"pwn4g3-hivemind","name":"J4K3 H!V3M!ND v0.0.4",...}`. **Not a
   vulnerability** — recorded here so the next pass doesn't re-flag it.

## Known gaps in this assessment

- The `169.254.169.254.nip.io` case was blocked by the *edge*, not the code, so
  that specific metadata-exfiltration path is mitigated by Cloudflare rather than
  by us. A different egress environment could expose it.
- The D1 data store (S6 in the original plan) was not reviewed — the audit is
  HTTP-surface only. `docs/ANALYSIS.md` covers what each table holds.
- The Discord Ed25519 and Stripe HMAC verification paths were not fuzzed. Both
  are security-critical and both are worth a dedicated pass.
- No port scanning, no subdomain enumeration, no third-party targets — the
  authorization covered this estate only.
